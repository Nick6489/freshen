# freshen-ffi

A C ABI for [freshen](../README.md), so hosts written in C, C++, C#, Objective-C,
Swift and other languages can use the same authenticated update flow. This crate
adds no update logic of its own; it exposes the library's operations through
opaque handles and status codes.

`include/freshen.h` is generated by `cbindgen` and committed. The crate builds a
`cdylib`, a `staticlib` and an `rlib`.

## Shape of the API

```text
freshen_updater_new ─► freshen_check ─► candidate ─► freshen_prepare ─► prepared
                                                                           │
             freshen_handoff_cancel ◄── handoff ◄── freshen_arm ◄─────────┘
                  (or quit; the helper installs, the new version calls
                   freshen_confirm_startup)
```

Everything blocks; run `freshen_check`, `freshen_prepare` and `freshen_arm` on a
worker thread. Read the crate documentation in `src/lib.rs` (or the top of the
generated header's function comments) for the full contract: handle ownership,
threading, string ownership, status codes and panic behavior.

## Custom transports

Pass a `FreshenTransport` when creating the updater to supply your own
downloads: authentication, offline storage, or test fixtures. The callback hands
bytes to a `FreshenSink` with `freshen_sink_write`. The sink is on the Rust side,
so the size limit, cancellation and progress reporting are enforced whatever the
callback does, and URLs that are not HTTPS (or that embed credentials) never
reach it. There is deliberately no switch to skip signature verification or
allow plain HTTP.

## Tests

`tests/c/harness.c` is a C program compiled with `-Wall -Wextra -Werror -pedantic`
against the generated header and the real shared library. `tests/c_harness.rs`
builds signed fixtures and runs it through in-process ABI checks and the same
parent / helper / restarted-application scenarios as `tests/helper_process.rs`
(commit, cancel, failed-startup rollback, unconfirmed timeout, busy lock).

The same scenarios run a second time with the C side built under AddressSanitizer
and UndefinedBehaviorSanitizer with leak detection on, which catches memory misuse
across the C/Rust boundary: use after free, double free, wrong-allocator frees,
leaks, out-of-bounds access and undefined behavior in the C code. (Only the C side
is instrumented; the Rust library is not. A test skips itself on toolchains that
cannot run sanitized programs.)

`tests/cpp/consumer.cpp` is a C++ consumer, the way a Qt or Win32 application would
write one, with RAII owners for every handle type. `tests/cpp_header.rs` checks the
generated header compiles as C++11, C++14, C++17 and C++20 under `-Wall -Wextra
-Werror -pedantic`, then builds and runs the consumer against signed fixtures, plain
and sanitized. The higher-level C++ wrapper, `bindings/cpp/include/freshen/freshen.hpp`,
is tested by `tests/cpp_wrapper.rs` (including a real Qt 6 program); see
`bindings/cpp/README.md`.

These tests are Unix-only for now. `tests/header.rs` runs everywhere and fails if
`include/freshen.h` no longer matches the source:

```text
FRESHEN_UPDATE_HEADER=1 cargo test -p freshen-ffi --test header
```

## Not yet covered

`shared::publish` / `shared::inspect` (synchronized installs) and the
`freshen-release` publisher tool are not exposed. Windows and macOS are built by
CI but the C harness does not run there yet; macOS application-bundle
installation in particular needs a signed bundle and is checked manually.
