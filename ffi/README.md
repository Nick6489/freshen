# freshen-ffi

A C ABI for [freshen](../README.md), so hosts written in C, C++, C#, Objective-C,
Swift and other languages can use the same authenticated update flow. This crate
adds no update logic of its own; it exposes the library's operations through
opaque handles and status codes.

`include/freshen.h` is generated by `cbindgen` and committed. The crate builds a
`cdylib`, a `staticlib` and an `rlib`.

## Shape of the API

```text
freshen_updater_new ─► freshen_check ─► candidate ─► freshen_prepare ─► prepared
                                                                           │
             freshen_handoff_cancel ◄── handoff ◄── freshen_arm ◄─────────┘
                  (or quit; the helper installs, the new version calls
                   freshen_confirm_startup)
```

Everything blocks; run `freshen_check`, `freshen_prepare` and `freshen_arm` on a
worker thread. Read the crate documentation in `src/lib.rs` (or the top of the
generated header's function comments) for the full contract: handle ownership,
threading, string ownership, status codes and panic behavior.

## Custom transports

Pass a `FreshenTransport` when creating the updater to supply your own
downloads: authentication, offline storage, or test fixtures. The callback hands
bytes to a `FreshenSink` with `freshen_sink_write`. The sink is on the Rust side,
so the size limit, cancellation and progress reporting are enforced whatever the
callback does, and URLs that are not HTTPS (or that embed credentials) never
reach it. There is deliberately no switch to skip signature verification or
allow plain HTTP.

## Tests

`tests/c/harness.c` is a C program compiled with `-Wall -Wextra -Werror -pedantic`
against the generated header and the real shared library. `tests/c_harness.rs`
builds signed fixtures and runs it through in-process ABI checks and the same
parent / helper / restarted-application scenarios as `tests/helper_process.rs`
(commit, cancel, failed-startup rollback, unconfirmed timeout, busy lock).

The same scenarios run a second time with the C side built under AddressSanitizer
and UndefinedBehaviorSanitizer with leak detection on, which catches memory misuse
across the C/Rust boundary: use after free, double free, wrong-allocator frees,
leaks, out-of-bounds access and undefined behavior in the C code. (Only the C side
is instrumented; the Rust library is not. A test skips itself on toolchains that
cannot run sanitized programs.)

`tests/cpp/consumer.cpp` is a C++ consumer, the way a Qt or Win32 application would
write one, with RAII owners for every handle type. `tests/cpp_header.rs` checks the
generated header compiles as C++11, C++14, C++17 and C++20 under `-Wall -Wextra
-Werror -pedantic`, then builds and runs the consumer against signed fixtures, plain
and sanitized. The higher-level C++ wrapper, `bindings/cpp/include/freshen/freshen.hpp`,
is tested by `tests/cpp_wrapper.rs` (including a real Qt 6 program); see
`bindings/cpp/README.md`.

`tests/boundary.rs` feeds the exported functions garbage: null for every pointer,
invalid UTF-8, undersized structs and unknown enums, absurd counts and lengths, extreme
numbers, a hostile transport, misused handles, the helper entry point with junk
arguments, corrupt state on disk, and 3,200 seeded random call steps. Every call must
return a defined status with a message: no crash, no hang, and no `FRESHEN_ERR_PANIC`
(the caught-panic code, which would mean bad input reached an `unwrap` or an overflow).
It found that the library trusted a few caller-supplied counts enough to read past the
caller's buffer before checking them; those are now refused first, and the limits are
documented on the struct fields. What no C API can detect (a non-null pointer that lies, a
count that overstates a real buffer, a double free, using a sink after its callback
returned) remains the caller's contract.

The C and C++ harness tests are Unix-only for now. `tests/boundary.rs` and
`tests/header.rs` run everywhere; `tests/header.rs` fails if `include/freshen.h` no
longer matches the source:

```text
FRESHEN_UPDATE_HEADER=1 cargo test -p freshen-ffi --test header
```

## Windows

`cargo build -p freshen-ffi` produces `freshen_ffi.dll` with its import library
(`freshen_ffi.dll.lib` on MSVC), and a static `freshen_ffi.lib`.

- **Dynamic:** include `freshen.h`, link the import library, and ship the DLL beside the
  executable (or use the .NET package, which does this for you).
- **Static:** also link the system libraries the Rust code needs. Ask cargo for the exact
  list with `cargo rustc -p freshen-ffi --release --crate-type staticlib -- --print
  native-static-libs`.
- **Strings are UTF-8**, including paths, which are converted for the OS. A path with
  unpaired UTF-16 surrogates cannot be expressed. For `freshen_run_helper`, pass arguments
  as UTF-8: take them from `wmain`'s wide `argv` (or `CommandLineToArgvW`) and convert, since
  the ANSI `main` receives them in the active code page and mangles non-ASCII text.
- **The installed executable must have an extension** (`.exe`): Windows cannot launch a file
  without one, and the helper restarts the application by path. A running executable also
  cannot be replaced, which is what the helper is for: it waits for the process to exit.

Windows CI has passed the Rust suite (including ABI boundary tests), the .NET
suite, and single-platform NuGet pack/consume checks. The C and C++ harnesses use
POSIX APIs and remain Unix-only; `freshen.hpp` has no MSVC consumer test. A green
Rust job on Windows does not establish C/C++ consumer coverage there.

## Not yet covered

`shared::publish` / `shared::inspect` (synchronized installs) and the
`freshen-release` publisher tool are not exposed. macOS application-bundle
installation needs a signed bundle and is checked manually.

See [testing and integration](../TESTING.md) for the coverage matrix, application
acceptance checks, and deferred review findings, including the status-output error
path leak.
